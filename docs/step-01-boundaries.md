# Step 01 — Test Boundaries

## แนวคิด

boundary คือการเลือกว่า test หนึ่งข้อจะเขียนให้แตะไกลแค่ไหน วิธีตัดสินที่ใช้ตลอดใน lab นี้คือถามว่า
ถ้า test ข้อนี้แดง เรารู้ไหมว่าพังเพราะอะไร และต้องเสียเวลากับความเปราะของ test เท่าไหร่ถึงจะรู้
ยิ่งแตะไกล ยิ่งมั่นใจว่าระบบทำงานจริง แต่ก็ช้ากว่าและหาจุดพังยากกว่า

ตัวอย่างที่เห็นชัดสุดคือบั๊ก `(12 - i)` ใน lab 00 พอใส่บั๊กนี้ unit test แดงแค่ข้อเดียว
และชื่อ test ก็บอกเลยว่าพังที่การคำนวณเลขตรวจ แต่ integration test แดงเหมือนกันโดยได้แค่
`Expected 201, Received 400` ซึ่ง 400 เกิดได้หลายสาเหตุ ต้องไล่เองว่าเป็นเพราะอะไร

สรุปแต่ละระดับตามที่เข้าใจ:
- Unit ตรวจกฎหรือการคำนวณชิ้นเล็กๆ ไม่แตะ DB หรือ HTTP เร็วและชี้จุดพังชัดที่สุด
- Integration ตรวจว่าโค้ดเราคุยกับของข้างนอกได้ถูก เช่น repository กับ Postgres จริง
  ปัญหาอย่าง map column ผิดหรือ constraint จะเจอเฉพาะตอนชนของจริง
- Component รันทั้ง service ผ่านทางเข้า (HTTP) แต่ของข้างนอกที่ไม่ใช่ของเราใช้ตัวแทนแทน
- Contract ตรวจว่าฝั่งที่เรียก API กับฝั่ง API ตกลงรูปร่างข้อมูลตรงกัน
- End-to-end เดินทั้งระบบเหมือนผู้ใช้จริง มั่นใจสุดแต่ช้าและเปราะสุด จึงควรมีน้อยข้อ

อีกเรื่องที่สังเกตได้ คือโฟลเดอร์ `test/integration/` ในระบบอ้างอิงชื่อ integration
แต่ test ข้างในยิง HTTP เข้า app แล้วต่อ Postgres จริง ซึ่งตามนิยามจริงๆ คือ component test
เลยตัดสินจากสิ่งที่ test ทำ ไม่ได้ดูจากชื่อโฟลเดอร์

## สรุป Part A

ตารางเต็มอยู่ที่ `labs/01-boundaries/worksheet.md` ตรงนี้เล่าเฉพาะข้อที่ตัดสินยาก

ข้อ 16 (ปิดหีบแล้วเปลี่ยนคะแนนไม่ได้) ตอนแรกคิดว่าเป็น unit เพราะดูเป็นแค่กฎเปลี่ยนสถานะ
แต่พอเปิด `voteRoutes.ts` ดู ไฟล์นี้เรียก `jwt.verify` กับ `pool.query` ตรงๆ ใน route
ไม่มีจุดให้ใส่ตัวแทน จึงแยกกฎมาทดสอบเดี่ยวไม่ได้ ต้องยิงผ่าน HTTP กับ Postgres จริง
เลยรู้ว่าระดับของ test ไม่ได้ขึ้นกับกฎอย่างเดียว แต่ขึ้นกับว่าโค้ดเขียนให้ทดสอบง่ายแค่ไหนด้วย
ถ้าแยกกฎไปเป็น service ที่รับ repository ผ่าน constructor ข้อนี้ก็จะลงมาเป็น unit ได้

ข้อ 2 (สมัครด้วยเขตที่ไม่มีในระบบ ได้ 400) แรกๆ ตอบว่า component แต่พออ่านโค้ดเปลี่ยนเป็น unit
เพราะ `AccountService.register` รับ `DistrictRepository` เข้ามาแล้วโยน `ValidationError` เอง
ใช้ตัวแทนที่คืน null ก็ตรวจกฎได้โดยไม่ต้องมี DB ส่วนการแปลง error เป็น 400 อยู่ใน error handler
ของ `app.ts` ซึ่งใช้ component test แค่ข้อเดียวยืนยันก็พอ ไม่ต้องทำซ้ำทุกกฎ

ข้อ 7 (หมายเลขผู้สมัครในเขตเดียวกันห้ามซ้ำ) เป็น integration เพราะตัวกันซ้ำจริงๆ คือ
`UNIQUE (district_id, number)` ในตาราง candidates (ดูใน `003-parties-candidates.sql`)
unit กับ stub ตรวจได้แค่ว่าโค้ดเรียกเช็ก แต่ไม่ได้ตรวจตัว constraint จึงต้องชน Postgres จริง

ข้อ 13 (ลงคะแนนพร้อมกัน 1,000 ครั้ง) กับข้อ 15 (หน้าสวยบนมือถือ) จัดเป็น X เพราะไม่ใช่
functional test อัตโนมัติ ข้อ 13 เป็น load test ต้องใช้เครื่องมืออย่าง k6 และต้องกำหนดเกณฑ์วัดก่อน
ส่วนข้อ 15 คำว่า "สวย" ไม่มีค่าให้ assert ต้องให้คนดูบนอุปกรณ์จริง

สิ่งที่ได้เรียนรู้เพิ่ม: component test ที่นี่ไม่จำเป็นต้องใช้ Postgres เสมอไป เพราะ
`createApp(deps)` รับ repository กับ token service จากข้างนอก เลยใช้ตัวแทนแบบ in-memory ได้
(ข้อ 4, 9, 12) ยกเว้น `voteRoutes` ที่ผูกกับ `pool` โดยตรง (ข้อ 14, 16) ซึ่งต้องใช้ Postgres จริง

### โค้ดที่ใช้ทดสอบ

ทดสอบ `Prototype.html` (หน้าจอลงคะแนนของผู้ใช้สิทธิเลือกตั้ง) ซึ่งไม่มี server, ฐานข้อมูล
หรือ session ตรรกะทั้งหมดอยู่ใน script ก้อนเดียว (state: `selected`, `confirmed`, `ballotClosed`)
test ระดับ unit จึงต้องแยกตรรกะออกมาเป็นฟังก์ชันก่อน (ดูหัวข้อ "สิ่งที่ต้องเปลี่ยนในโค้ด")

### เหตุผลของแต่ละชั้น

- Unit (TC-04, 05, 08, 11, 14): ทั้งห้าข้อเป็นกฎของการเลือกและยืนยัน ผลขึ้นกับ state ที่ส่งเข้าไป
  อย่างเดียว ไม่ต้องใช้ DOM จึงเร็วและเมื่อแดงชื่อ test ชี้ไปที่กฎข้อเดียว TC-04 ใช้ spy
  ดูว่ามีการแจ้งเตือนสำเร็จ TC-08 ใช้ stub ของตัวบันทึกคะแนน TC-11 ใช้ mock ยืนยันว่าเมื่อหีบปิด
  ตัวบันทึกคะแนนถูกเรียก 0 ครั้ง
- Component (TC-12, 21): สองข้อนี้ตรวจสิ่งที่ผู้ใช้เห็นบนหน้าจอ (แถบล็อก การ์ดไม่ตอบสนอง
  ป้ายสถานะเปลี่ยน) ต้องมี DOM จึงโหลดหน้าใน jsdom แล้วคลิกการ์ดและปุ่มจริง
  ไม่ต้องเปิดเบราว์เซอร์
- E2E (TC-04→08→12): เดินทั้ง journey บนเบราว์เซอร์จริงด้วย Playwright ใช้ยืนยันว่า
  ทุกส่วนทำงานร่วมกันได้ มีข้อเดียวเพราะช้าและเปราะที่สุด
- ไม่มี Integration และ Contract: โค้ดนี้ไม่มีของภายนอกให้คุยด้วย (ไม่มี DB หรือ API)
  ระดับเหล่านี้จะเกิดขึ้นเมื่อมี Backend

### รูปร่างของ test suite

```
        /\         e2e         : 1 ข้อ
       /  \        component   : 2 ข้อ
      /    \       integration : 0 ข้อ
     /______\      unit        : 5 ข้อ
```

### คำตอบ

1. รูปร่าง: เป็น pyramid เพราะ unit มากที่สุด (5) แล้วลดลงเป็น component (2) และ e2e (1)
   แต่ที่ชั้น integration ว่างเพราะโค้ดไม่มีของภายนอก ส่วนที่ยังไม่ครอบคลุมจากเอกสาร
   22 ข้อคือ TC-16, 17 (ออกจากระบบแล้วกลับมาคะแนนต้องคงเดิม) ซึ่งเขียน test ไม่ได้
   เพราะ state อยู่ในหน่วยความจำ รีเฟรชหน้าแล้วหาย นี่เป็นช่องว่างของโค้ดเทียบกับ FR-09 และ FR-10

2. e2e ที่ลองเขียนใหม่ให้ต่ำลง:

   TC-04→08→12 (journey ลงคะแนน เปลี่ยน และปิดหีบ) แตกได้เป็น 2 ระดับ: กฎของแต่ละขั้น
   (ลงครั้งแรก, เปลี่ยนคะแนน, ปฏิเสธเมื่อปิดหีบ) ทดสอบเป็น unit ได้ (TC-04, 08, 11)
   ส่วนพฤติกรรมบนหน้าจอ (แถบล็อก การ์ดไม่ตอบสนอง) ทดสอบเป็น component ได้ (TC-12)
   ทำให้ e2e เหลือไว้เป็น smoke test 1 ข้อเพื่อยืนยันว่าทุกส่วนต่อกันได้

   TC-16, 17 (คะแนนต้องคงเดิมเมื่อกลับเข้าระบบหรือใช้หลายอุปกรณ์) ตอนนี้เป็น e2e ที่ทำไม่ได้
   เมื่อมี Backend จะลงมาเป็น integration test ของ repository ว่าบันทึกแล้วอ่านกลับได้
   ค่าเดิม และ component test ว่า API คืนค่าเดิมให้ผู้ใช้คนเดิม

### สิ่งที่ต้องเปลี่ยนในโค้ด

แยกตรรกะออกจาก DOM เป็นโมดูลฟังก์ชันล้วน (เช่น `select`, `canConfirm`, `confirm`, `setClosed`)
ที่รับ state เข้ามาและคืน state ใหม่ แล้วให้ตัวบันทึกคะแนนกับตัวแจ้งเตือน (toast) เป็น
dependency ที่ส่งเข้าไป เพื่อให้ใส่ stub, spy และ mock ได้ ส่วนหน้า HTML เหลือหน้าที่
เรียกฟังก์ชันและวาดหน้าจอ
